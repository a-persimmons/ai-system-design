# 预填充与解码 {#prefill-and-decode-the-two-phases-of-llm-inference}

现在，让我们了解为什么 TTFT 和 TPS 的行为如此不同。答案在于 LLM 如何实际响应请求。每个请求都会经历两个不同的阶段。

- **预填充** 为第一期。它读取并处理整个输入提示词。
- **解码** 是第二期。它一次生成一个输出 token。

简而言之， **预填充是读取我们问题的模型，解码是编写答案的模型。** 我们有一篇关于 [Prefill 与 Decode](https://outcomeschool.com/blog/prefill-vs-decode-llm-inference-optimization) 的详细博客，逐步解释了这两个阶段。

两个阶段都使用完全相同的模型和完全相同的权重。只是这两个阶段的工作方式不同，而这个微小的差异会改变一切。

## 预填充 {#prefill}

**预填充是模型一次性读取和处理整个输入提示词并生成第一个输出 token.** 的阶段

假设一名学生走进考场。在写任何东西之前，学生默读整张试卷。这篇通篇阅读的部分是预填充。

由于整个提示词是预先已知的，因此该模型可以同时处理每个输入 token。在读取提示词的同时，它还计算并存储每个输入 token 的键 (K) 和值 (V)。所有这些存储的键和值一起形成了 **KV 缓存** （我们很快就会详细了解它）。在预填充末尾，模型生成第一个输出 token。

**预填充是计算密集型的。** 它将大数字表与大数字表相乘，这正是 GPU 的构建目的。 GPU 的数学单元仍然非常繁忙，在大型提示词上通常接近 90% 或更多。

更长的提示词意味着更长的预填充。因此， **更快的预填充意味着我们更快地看到第一个token（较低的TTFT）。**

## 解码 {#decode}

**解码是模型一次生成一个输出 token 的阶段，重用预填充准备的 KV 缓存。**

继续我们的考试示例，学生现在开始逐字写下答案。这种缓慢的逐字书写是解码。

在解码中，每步仅处理一个 token。一个 token 的计算量很小。但即使要生成一个 token，GPU 仍必须从内存中读取整个模型权重和整个增长的 KV 缓存。因此，GPU 大部分时间都在等待数据到达，而其数学单元对于单个请求的繁忙程度仅为 20% 到 40% 左右。

**解码受内存带宽限制。** 想象一下一位厨师必须走进一个巨大的食品储藏室，拿起一种原料，然后走回来，切碎它，然后重复，每次只使用一种原料。来回行走（从内存中移动数据）比砍伐（微小的数学）花费的时间要长得多。

对于典型的请求，预填充在不到一秒的时间内完成，但解码可以运行几秒钟。因此， **更快的解码意味着我们更快地看到答案的其余部分（较低的TPOT）。**

让我将预填充和解码之间的差异制成表格，以便您更好地理解。

| 比较项 | 预填充 | 解码 |
| --------------- | ------------------------------------------------------- | ----------------------------------------------------- |
| 作用 | 处理整个输入提示词 | 逐一生成输出 token |
| 并行 | 并行（一次所有提示词 token） | 顺序（一次一个 token） |
| 步骤 | 一大步 | 许多小步骤 |
| 瓶颈 | 计算受限，取决于运算速度 | 内存带宽受限，取决于数据传输 |
| GPU 利用率 | 高（数学单元繁忙，可以接近 90% 或更多） | 低（数学单元大部分空闲，大约 20% 到 40%） |
| KV 缓存操作 | 写入高速缓存 | 读取并扩展高速缓存 |
| 延迟指标 | 首 token 延迟 (TTFT) | 每个输出 token 的耗时 (TPOT) |
| 成本来源 | 随提示词长度增长 | 每一步都要读取全部权重及 KV 缓存 |

这个拆分解释了很多AI 系统设计。这就是为什么输入 token 比输出 token 便宜。这就是为什么长提示词会使第一个 token 变慢。这就是为什么如此多的优化集中在解码阶段。

## 分块预填充 {#chunked-prefill}

但是，这里有一个问题。当预填充和解码运行在同一个GPU上时，它们会互相争斗。很长的提示词的预填充可以作为一大步运行。当这一巨大步骤运行时，它会占用 GPU 并冻结已经处于解码阶段的其他用户的 token 流。他们的回答结结巴巴。

**分块预填充** 将一个长的提示词的预填充分成几个较小的文本块，并在文本块之间插入小的解码步。

```
WITHOUT chunked prefill:
  long prompt: [============= ONE BIG PREFILL =============]
  other users: tok ....... (frozen, stuttering) ....... tok

WITH chunked prefill:
  long prompt: [chunk 1][chunk 2][chunk 3][chunk 4][chunk 5]
  other users: tok   tok   tok   tok   tok   tok
                  ^ a decode step slips in between the chunks
```

在这里，我们可以看到一个巨大的预填充冻结了其他用户，而分块预填充让他们的 token 继续在文本块之间流动。这就像一个厨师只有一个炉子。如果一位顾客订了一顿丰盛的宴会，一次烹饪所有的食物就会冻结其他桌子上的食物。相反，厨师会小批量地烹饪宴会，并在它们之间插入快速的单道菜。

**注：** 分块预填充可防止正在进行的应答停止。它不会使预填充本身更快。

## 预填充与解码分离 {#prefill-decode-disaggregation}

从大范围来看，我们可以更进一步。因此，[**预填充与解码分离**](https://outcomeschool.com/blog/prefill-decode-disaggregation) 来救援。

**预填充与解码分离 = 预填充 + 解码 + 分解** ，其中分解只是意味着将连接在一起的事物分开。

**预填充与解码分离是在单独的 GPU 上运行预填充阶段和解码阶段的技术，这样它们就不会争夺相同的硬件。**

简而言之，我们有一组 GPU 的唯一工作是读取提示词，另一组 GPU 的唯一工作是写入答案。主要有四个部分：

- **路由器：** 接收每个请求并决定哪个预填充工作程序和哪个解码工作程序将处理它。
- **预填充工作人员：** GPU，仅执行预填充。他们加工提示词，生产出第一批 token，并构建 KV 缓存。它们针对繁重的计算进行了调整。
- **解码工作人员：仅执行解码操作的** GPU。他们收到 KV 缓存并一次生成一个答案 token。它们经过调整以实现快速内存访问。
- **KV 缓存转：** 两者之间的桥梁。 预填充工作线程通过 NVLink、InfiniBand 或 RDMA 等非常快的连接将 KV 缓存发送到解码工作线程。

流程如下所示：

```
Request
   |
   v
[Router] --> picks a Prefill worker and a Decode worker
   |
   v
[Prefill worker] --> reads the full prompt
                 --> builds the KV Cache
                 --> produces the first token
   |
   v  (KV Cache is sent over the network)
   |
[Decode worker]  --> loads the KV Cache
                 --> writes token 2, token 3, token 4 ...
   |
   v
Answer streamed to the user
```

为了便于理解，我们以一个带有示例数字的请求为例。用户发送 4000 token 的提示词，答案的长度将为 200 token。 预填充工作进程在 400 毫秒内处理所有 4000 个 token，并生成第一个 token 以及一个 2 GB 的 KV 缓存。用户看到答案开始，因此我们的 TTFT 约为 400 毫秒。 2 GB KV 缓存在 20 到 50 毫秒内复制到解码工作线程。然后，解码工作进程在 20 毫秒内生产每个 token，因此 200 个 token 大约需要 4 秒。 预填充工作线程已经转移到下一个用户的提示词，并且解码工作线程永远不会被大预填充打断。

因此，用户可以同时获得快速启动（低 TTFT）和流畅流程（低 TPOT）。

让我将共置服务和分类服务之间的差异制成表格，以便您更好地理解，以便您可以根据您的用例决定使用哪一种。

| 比较项 | 混合部署 | 分离部署 |
| ---------------------------- | ---------------------------------------- | ------------------------------------- |
| 预填充和解码运行的地方 | 相同的 GPU | 独立的预填充和解码工作进程 |
| 两阶段之间的干扰 | 有，预填充会阻塞解码 | 无 |
| TTFT 与 TPOT | 需要权衡，改善一个可能损害另一个 | 可以分别优化 |
| 扩展 | 两个阶段一起扩展 | 每个阶段独立扩展 |
| KV 缓存传输 | 不需要 | 每个请求都需要 |
| 网络要求 | 无额外要求 | 必须有高速互连 |
| 复杂性 | 低 | 高 |
| 最适合 | 小规模、单 GPU、短提示词 | 大规模、多用户、长提示词 |

对于小型设置，单 GPU 上的分块预填充更简单且足够好。对于大型设置，分解是最佳选择。 SGLang 等服务系统开箱即用地支持它。
