# AI 系统的缓存 {#caching-in-ai}

人工智能中的缓存比常规系统中的缓存丰富得多。任何缓存的基本形状都是相同的。对于每个请求，我们首先检查缓存。如果数据存在（ **缓存命中** ），我们将返回它而不调用LLM。如果不是（ **缓存未命中** ），我们调用LLM，将结果存储在缓存中，并返回答案。

```
Cache Hit (data already cached, skip the LLM)

   Client  --->  Server  --->  Cache
                                  |
                                  | (found)
                                  v
   Client  <---  Server  <-----  Cache


Cache Miss (data not in cache, call the LLM and store)

   Client  --->  Server  --->  Cache
                                  |
                                  | (not found)
                                  v
                  Server  --->  LLM
                                  |
                                  v
                  Server  --->  Cache (store for next time)
                                  |
   Client  <---  Server  <--------+
```

缓存的优势在于缓存命中和缓存未命中之间的差距大小。在 AI 中，这种差距是巨大的——在 Redis 中，一次命中会花费几毫秒的时间，一次未命中会花费我们一次完整的 LLM 调用（秒和 token）。

我们有四种主要类型的缓存。

## KV 缓存 {#kv-cache}

这是AI中最重要的缓存。我们有一篇关于 [KV Cache](https://outcomeschool.com/blog/kv-cache-in-llms) 的详细博客，从头开始解释它。

当 LLM 一次生成一个 token 时，对于每个新的 token，模型必须查看所有先前的 token。如果我们为每个新的 token 从头开始​​重新计算所有内容，速度会非常慢。

在注意力层内部，每个 token 都被转换为 **Query (Q)** 、 **Key (K)** 和 **Value (V)** 。当前的 token 使用其查询与所有先前 token 的 Key 进行比较，然后从相关的 Key 中收集 Value。因此，模型在每一步都需要之前所有 token 的键和值。

如果没有缓存，模型将在每一步重新计算之前每个 token 的键和值。让我们通过运行示例来看看这一点：

- **第1步：** 输入“我爱”。模型计算“我”和“爱”的 K、V、Q。预示“教”。
- **第2步：** 输入“我喜欢教学”。模型重新计算“I”和“love”的 K 和 V（已在步骤 1 中计算），并计算新 token“教学”的 K、V、Q。预言“AI”。
- **第3步：** 输入是“我喜欢教人工智能”。模型重新计算“I”、“love”和“teaching”（全部已计算）的 K 和 V，并计算新 token“AI”的 K、V、Q。

该模型正在重复已经见过的 token 的相同工作。这是浪费计算。

你看到问题了吗？我们付钱给 GPU 来重做它已经完成的工作。

该存储存储器称为 [**KV 缓存**](https://outcomeschool.com/blog/kv-cache-in-llms)。这个想法很简单：计算每个 token 的键和值一次，存储它们，并在以后的每个步骤中重用它们。

可以将其想象为在会议中做笔记。每当新人发言时，我们不会要求所有之前的发言者重复他们所说的话，而是简单地阅读笔记并只听新发言者的发言。笔记是缓存。

从实数角度来看，如果模型生成 100 个 token，没有 KV 缓存，则键和值的总计算量为 `2 + 3 + 4 + ... + 100 = 5,049`。有了KV 缓存，就是`2 + 1 + 1 + ... + 1 = 101`。这大约是 **计算量** 的 50 倍。序列越长，节省的费用就越大。

我们只缓存 Key 和 Value，不缓存 Query。在自回归生成过程中，Query 只用于 **当前正在生成的 token** 。预测完成后，这个 Query 就不再需要了。但之前每个 token 的 Key 和 Value，在 **之后的每一步** 中都需要使用。

KV 缓存显著加快了生成速度，但只要对话还在进行，它就必须一直驻留在显存中。长对话的 KV 缓存可能占用数 GB 空间。因此，我们无法在同一台机器上同时处理太多长对话。我们有一篇关于 [LLM 如何使用 GPU 显存](https://outcomeschool.com/blog/llm-gpu-memory) 的详细文章，解释模型权重、KV 缓存以及其他开销如何共同构成显存总占用。

为了更高效地管理 KV 缓存占用的显存，现代推理服务器采用 **[分页注意力（Paged Attention）](https://outcomeschool.com/blog/paged-attention-in-llms)** ，其思想与操作系统管理内存相同。它不会提前为每个请求预留一整块大内存——由于无法预知响应长度，这会浪费大量空间——而是随着响应增长，按需分配固定大小的 KV 缓存 **页** 。

可以把它想象成一家酒店：客人入住时不知道会住几晚。传统做法为每位客人连续预留 30 间房，即使大多数人只住两晚，结果上百间房都空着。分页做法则按需逐间分配，只要有空房就可以使用。酒店维护一张清单（页表），记录哪些房间属于哪位客人。KV 缓存也是如此：相同的显存容量可以服务更多用户。

## KV 缓存压缩 {#kv-cache-compression}

分页注意力避免了显存浪费，但 KV 缓存本身仍然非常大。以一个接近 Llama 2 的模型为例：32 层、32 个注意力头，每个头的 Key 和 Value 各包含 128 个数，每个数占 2 字节。看看它到底有多大。

```python
layers = 32
heads = 32
head_dim = 128
bytes_per_number = 2

# Key and Value, so multiply by 2
per_token = 2 * layers * heads * head_dim * bytes_per_number
print(per_token / (1024 * 1024))  # 0.5 MB
```

这里将层数、注意力头数、每个头的维度和每个数的字节数相乘。因为同时存储 Key 和 Value，还要乘以 2。因此，每个 token 需要 0.5 MB。

一段 4,000 token 的对话需要 2 GB。一个 100,000 token 的文档需要 50 GB，而这还只是一个用户的缓存。GPU 显存通常为 24 GB 到 80 GB，其中很大一部分已经被模型权重占用。 **KV 缓存随文本长度和用户数量增长，不断消耗 GPU 显存。**

这时，[**KV 缓存压缩**](https://outcomeschool.com/blog/kv-cache-compression) 就派上了用场。 **KV 缓存压缩是一组减小 KV 缓存体积、同时使模型输出质量基本保持不变的技术。**

下面用表格比较四种主要方法，便于理解。

| | 量化 | token 淘汰 | 跨注意力头共享 | 低秩压缩 |
| ------------------- | --------------------- | ------------------- | ------------------------------- | ------------------------ |
| 如何节省显存 | 每个数使用更少的比特 | 存储更少的 token | 每层保留更少的 Key 和 Value | 每个 token 使用更小的向量 |
| 需要重新训练 | 否 | 否 | 是 | 是 |
| 丢弃 token | 否 | 是 | 否 | 否 |
| 典型节省 | 2x 至 4x | 固定缓存大小 | 4x 至 8x | 10x 或更多 |
| 质量损失 | 非常少 | 取决于任务 | 非常少 | 几乎没有 |
| 示例 | KIVI | H2O、StreamingLLM | GQA、MQA | MLA (DeepSeek) |

因此，根据我们的用例：

- 如果我们正在运行现有模型并希望快速节省内存，请使用缓存的 **量化** 。
- 如果我们有一个很长的对话，或者不断出现没有结束的文本，请使用 **token 淘汰** 和 [Attention Sinks](https://outcomeschool.com/blog/how-do-attention-sinks-work)。
- 如果我们需要准确回忆长文档中的所有内容，请不要使用 token 逐出。
- 如果我们正在训练新模型，请从第一天开始在设计中使用 **GQA** 或 **MLA** 。

**注：** GQA（[分组查询注意力](https://outcomeschool.com/blog/grouped-query-attention)）和MQA（多查询注意力）让许多注意力头共享相同的键和值，MLA（多头潜在注意力）为每个token存储一个小的压缩向量，而不是完整的键和值。我们将在推理优化中详细了解 GQA。

这些方法可以结合起来。较小的 KV 缓存意味着每个 GPU 有更多用户、更长的上下文和更快的解码，而且无需购买更大的 GPU。

## 提示词缓存 {#prompt-cache}

许多应用程序在每次请求时都会发送相同的长系统提示词。

示例：客户支持机器人有一个解释规则的 3000-token 系统提示词。每条用户消息都带有相同的系统提示词。

如果没有提示词缓存，推理服务器会针对每个请求处理这 3000 个 token。

通过 [提示缓存](https://outcomeschool.com/blog/how-does-prompt-caching-work)，推理服务器处理系统提示词一次并存储结果。对于具有相同提示词的下一个请求，它将重用存储的结果并仅处理新的用户消息。

实际存储的是该共享开头的 KV 缓存，称为 **前缀** 。这就是为什么提示词缓存也称为 **前缀缓存** ，以及为什么它削减了预填充工作和 TTFT。这就像一位老师在每堂课开始时在黑板上写下同样长的指示。老师不会每次都重写它们，而是保留黑板的照片并重复使用它。

**注意：** 提示词缓存仅当请求共享完全相同的开头时才有帮助。因此，我们必须将固定部分（系统提示词、工具定义、长文档）放在提示词的开头，将变化部分（用户消息）放在末尾。

OpenAI 和 Anthropic 都支持提示词缓存。它可以将输入成本最多降低 90%，并显著缩短首 token 延迟（TTFT），让系统设计更轻松。

## 语义缓存 {#semantic-cache}

这是 AI 特有的缓存方式。

假设两位用户分别问：

- “法国的首都是什么？”
- “告诉我法国的首都是哪座城市。”

这两个句子不同，但意思相同。普通缓存会因为输入字符串不同而调用两次 LLM。

[语义缓存](https://outcomeschool.com/blog/how-does-semantic-caching-work) 会将每个查询转换为嵌入向量，并存储向量及其对应响应。新查询到来时，先将它转换为嵌入向量，再在缓存中搜索相似向量。如果找到足够相近的匹配，就直接返回缓存的响应，无须调用 LLM。

这样可以降低成本和延迟。

但有一个问题：“足够相近”并不总是“相同”。因此必须谨慎设置 **相似度阈值** 。

- 阈值过高，例如 `0.99`，几乎没有查询能匹配。只有完全相同的内容才可能通过，大部分缓存收益也就消失了。
- 阈值过低，例如 `0.50`，差别很大的问题也会匹配。“法国的首都”可能错误地匹配“德国的首都”，返回错误的城市。

对许多应用来说，`0.85` 到 `0.95` 左右的阈值效果不错，但合适的取值取决于使用场景。必须用真实用户的问题测试并调整。

> 阈值越高，匹配越少，但答案更稳妥；阈值越低，匹配越多，但答错的概率也更高。

**注意：** 如果答案依赖私有数据，绝不能在不同租户或用户之间共享语义缓存。“我的账户余额是多少？”绝不能用其他人的缓存条目来回答。

## 嵌入缓存 {#embedding-cache}

构建 RAG 系统（稍后会介绍）时，需要将大量文档转换为嵌入向量。计算嵌入向量本身也是一项成本较高的操作。

我们可以将常见查询和文档的嵌入向量缓存到 Redis 或其他键值存储中。键是文本或其哈希值，值是嵌入向量。我们有一篇关于 [嵌入缓存如何工作](https://outcomeschool.com/blog/how-does-an-embedding-cache-work) 的详细文章，解释缓存键的构造方式。

**注意：** 缓存键还必须包含嵌入模型的名称和版本。同一段文本在不同模型中会产生不同向量，混用它们会在不易察觉的情况下破坏搜索结果。

下次遇到相同文本时，直接从缓存读取嵌入向量，无须重新计算。

概括来说：

- **KV 缓存** 加快单次请求内部的下一个 token 生成。
- **提示词缓存** 加快不同请求之间重复出现的长提示词的处理。
- **语义缓存** 在相似问题已有答案时，完全跳过 LLM 调用。
- **嵌入缓存** 在再次遇到相同文本时，跳过嵌入模型调用。
