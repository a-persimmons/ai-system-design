# 多智能体系统 {#multi-agent-systems}

有时单个智能体是不够的。任务太大，系统提示词变得太长，或者工具数量变得难以管理。然后我们转向 **[多智能体系统](https://outcomeschool.com/blog/multi-agent-systems)** - 一组由 LLM 驱动的智能体，每个智能体都有自己的角色，共同完成一项共享任务。

简单来说：

**多智能体系统 = 专业化智能体 + 一种沟通方式 + 一种协调方式。**

将多智能体系统想象为电影制作团队。导演决定拍摄什么。电影摄影师操纵摄影机。演员们表演。编辑器将所有内容放在一起。没有一个人包办一切。每个专家都拥有自己的作品。这部电影的上映是任何一个人都无法单独制作的。

单个智能体是独奏厨师。 多智能体系统是一间完整的餐厅 - 厨房、餐厅、主人等等。

## 三大支柱 {#the-three-pillars}

每个多智能体系统都建立在三个支柱之上。去掉任何一个，它就会散架。

**支柱 1：专业化。** 每个智能体都有一个重点作用。其中一位智能体是研究员。另一个是作家。另一个是审稿人。这使得每个智能体和系统提示词都较小。该工具集保持相关性。该行为保持可靠。

**Pillar 2：通信。** 智能体必须能够共享信息。我们通过消息、共享内存或结构化切换来做到这一点。如果没有通信，智能体就无法构建彼此的工作。我们有一篇关于 [AI 智能体如何通信](https://outcomeschool.com/blog/how-ai-agents-communicate) 的详细博客，其中解释了消息格式和协议。

**支柱 3：协调。** 必须有人决定接下来由谁来做。必须有人决定任务何时完成。这可以是专用的编排器智能体、固定的工作流程或一组路由规则。

## 常见智能体角色 {#common-agent-roles}

大多数多智能体系统重用一小组角色：

- **编排者：** 接收用户请求，将其分解为子任务，委派它们，然后组合结果。
- **Worker：** 擅长完成一种任务的专家智能体（研究员、作家、编码员、数据分析师）。
- **路由器：** 查看请求并决定由哪个工作人员处理该请求。
- **规划者：** 生成一个分步计划，然后由工作人员执行。
- **Critic 或审阅者：** 检查另一个智能体的输出的质量、安全性或正确性。
- **工具专家：** 拥有特定工具或数据源的提示策略和模式知识（例如，深入了解模式并写出良好SQL的“数据库智能体”）。

## 具体示例：客户支持 {#a-concrete-example-customer-support}

假设我们想要一个处理客户支持电子邮件的系统。我们可以将工作分成四个智能体：

- **编排者** 收到一封客户电子邮件，例如“我想要为我的上一个订单退款，它到达时已损坏”。
- 它将查找工作交给 **研究工作者** ，后者提取订单详细信息、退货政策和客户的帐户历史记录。
- 它将收集到的笔记交给 **撰写工作者** ，后者起草个性化回复。
- 它将草稿交给 **评审者** ，检查语气、准确性和政策合规性，并在需要时将其发回进行修改。
- 一旦 Critic 批准，Orchestrator 就会向客户发送最终答复。

```
Customer Email
    |
    v
Orchestrator
    |
    v
Researcher --> notes
    |
    v
Writer --> draft
    |
    v
Critic --> approve or revise
    |
    v
Final Reply
```

四个智能体，每个都有一项工作。研究人员不知道如何撰写回复。笔者不知道如何查找客户数据。评论家不知道如何从头开始起草。每个智能体都有一个小型、聚焦的系统提示词。试图兼顾所有四项工作的单个智能体不太可靠。

## 协调模式 {#coordination-patterns}

智能体的运行方式有五种常见模式。

```
Sequential:    A -> B -> C -> D

Parallel:      Request
                 |
             +---+---+
             |   |   |
             A   B   C
             |   |   |
             +---+---+
                 |
              Merge -> Response

Router:        Request -> Router -> (A or B or C)

Hierarchical:       Orchestrator
                    /     |     \
                   A      B      C

Graph:          A <--> B
                ^      ^
                v      v
                C <--> D
                (any agent can call any other)
```

- **Sequential：** 智能体依次运行。每个智能体都建立在前一个的输出之上。简单的。易于调试。如果这些步骤可以并行运行，那么速度会很慢。
- **并行：** 多个智能体同时处理独立的子任务。结果在最后合并。快速 - 但前提是子任务真正独立。
- **路由器：** 路由器智能体选择哪个工作进程处理每个请求。当请求属于几个不同的类别时很好。
- **层级式：** 编排者将任务委派给工作者，工作者又可以继续委派给下级工作者。这很像真实公司的组织结构。
- **图或网络式：** 任意智能体都可以根据当前任务调用其他智能体。灵活性最高，但更难调试。

这些模式的一端是固定工作流，如顺序和并行；另一端是完全动态、由智能体控制的执行方式，如图模式。大多数系统位于两者之间。

## AI 子智能体 {#ai-subagents}

真实产品中，层级式模式最常见的形式就是子智能体。

**[AI 子智能体（SubAgent）](https://outcomeschool.com/blog/ai-subagents) 是在主智能体之下工作的较小型专用智能体，负责大任务中的某个具体部分。**

简单来说，主智能体像管理者，子智能体像团队成员。假设主智能体帮助规划旅行，它可以调用一个子智能体查航班，另一个查酒店，再由其他子智能体制定行程、查询天气。每个子智能体专注一项工作，并将其做好。

需要子智能体有四个原因：

- **上下文过载：** 单个智能体处理所有步骤时，上下文窗口很快就会填满，并开始忘记先前步骤。每个子智能体在独立的新上下文中工作，只返回简短结果。
- **专注：** 只有少量工具的子智能体，比持有大量工具的单一智能体更容易作出正确决策。
- **可复用性：** “网页搜索子智能体”可以被研究、新闻和购物智能体共同复用。
- **并行工作：** 一个子智能体查询航班时，另一个可以同时查看酒店。

流程很简单：主智能体拆分任务，将各部分发送给合适的子智能体；子智能体使用自己的工具和预算运行独立循环；最后，主智能体汇总结果，形成最终答案。

**注意：** 子智能体还可以调用其他子智能体，形成树状结构。这很强大，但必须谨慎使用，避免形成过深且成本高昂的调用链。

## 权衡 {#trade-offs}

多智能体系统处理复杂任务的能力更强，但延迟、token 消耗和调试成本也更高。常见问题包括：智能体交流很多却没有进展、错误在智能体之间传播，以及评审循环失控、始终无法收敛。

下面用表格比较单智能体与多智能体系统，便于根据使用场景作出选择。

| 属性 | 单智能体 | 多智能体系统 |
| ------------------------ | --------------------------------------------- | -------------------------------------------- |
| 复杂度 | 低 | 高 |
| 系统提示词 | 一个，可能变得很长 | 多个，每个各有侧重 |
| 每个智能体的工具数 | 所有工具集中在一个智能体上 | 工具分配给不同智能体 |
| 并行能力 | 有限，在一个循环内并行调用工具 | 各智能体自然地独立工作 |
| 调试 | 更容易（一个循环） | 更难（许多循环、切换） |
| 延迟 | 简单任务较低 | 任务交接会增加延迟，并行执行可降低延迟 |
| 成本 | 较低 | 较高 |
| 复杂任务的质量 | 会随着工具的增长而降低 | 通过专业化更好地扩展 |
| 故障模式 | 整体故障 | 部分故障或级联错误 |
| 最适合 | 简短、目标集中的任务 | 复杂、需要多种技能的任务 |

经验法则很简单： **从单个智能体开始。仅当单个智能体明显无法完成这项工作时，才转向多个智能体。当我们这样做时，添加解决问题的最小数量智能体。**

LangGraph 和 AutoGen 等框架处理大部分连接，因此我们不必从头开始构建编排层。

## A2A（智能体2智能体协议） {#a2a-agent2agent-protocol}

现在，让我们看看当智能体跨越组织边界时会发生什么。当我们所有的智能体都位于相同的代码库并使用相同的框架时，沟通就很容易。但是，如果我们的智能体是由不同的团队、不同的框架、不同的供应商构建的呢？他们如何互相交谈？

因此， **A2A（智能体2智能体协议）** 来救援。 A2A 是 Google 于 2025 年推出的开放标准（现隶属于 Linux 基金会），用于跨供应商智能体通信。超过 50 家公司（Atlassian、Cohere、Salesforce、SAP、Workday 等）支持它。

简而言之， **A2A 是一个智能体与另一个智能体通信的标准方式，即使它们是由不同的团队或供应商构建的。**

A2A 将其他智能体视为 **黑盒智能体** ：每个智能体暴露其可以做什么，但不暴露其内部逻辑、提示词或工具。这就像为我们没有编写的服务调用 REST API - 我们只知道该服务做什么以及如何与其通信。

## A2A 的运作方式 {#how-a2a-works}

每个 A2A 智能体都会发布一个 **智能体 Card** ，这是一个小的 JSON 文档，描述：

- 智能体的名称和描述
- 它提供的技能（带有输入和输出模式）
- 要连接的端点
- 它支持的身份验证和流媒体模式

其他智能体发现智能体卡，确定该智能体是否适合该任务，然后使用 **JSON-RPC over HTTP** 发送请求（一种通过发送命名函数及其参数的小 JSON 消息来调用另一台计算机上的函数的简单方法）。

A2A支持三种交互模式：

- **同步请求和响应：** 用于快速任务。
- **Streaming (SSE)：** 适用于部分结果流回的长时间运行任务。
- **A同步推送通知：** 适用于需要几分钟或几小时并在完成后给我们回电的任务。

## MCP 和 A2A 如何结合在一起 {#how-mcp-and-a2a-fit-together}

这是最常出现的问题，所以我们来解决一下。

- **MCP** 用于将智能体连接到 **工具和数据源** （数据库、API、文件系统）。
- **A2A** 用于将智能体与 **和其他智能体** 作为对等连接。

两者都是开放标准。它们是互补的，而不是竞争的。

现代 AI 系统设计通常同时使用两者：MCP 用于工具层，A2A 用于多智能体层。

```
+---------+    A2A    +---------+    A2A    +---------+
| Agent A | <-------> | Agent B | <-------> | Agent C |
+---------+           +---------+           +---------+
     |                     |                     |
     | MCP                 | MCP                 | MCP
     v                     v                     v
+---------+           +---------+           +---------+
| Tools/  |           | Tools/  |           | Tools/  |
| Data    |           | Data    |           | Data    |
+---------+           +---------+           +---------+
```

每个智能体使用 MCP 与其自己的工具进行对话。 智能体使用 A2A 相互通信。

对于大多数内部多智能体系统（其中所有智能体都在同一代码库中），我们不需要 A2A。当智能体跨越组织或框架边界时，我们需要它。
