# 嵌入向量流水线 {#embeddings-pipeline}

对于 RAG 和语义搜索，我们需要嵌入大量文档。

如果我们有一百万个文档，每个文档有 10 个文本块，那么我们就有 1000 万个嵌入向量需要计算。这是一项大批量工作。

嵌入向量管道如下所示：

```
Source Data (S3, DB, web)
    |
    v
Chunker (split documents into smaller pieces)
    |
    v
Embedding Model (compute embedding for each chunk)
    |
    v
Vector DB (store embeddings with metadata)
```

该管道在后台作为批处理作业运行。我们使用：

- Apache Spark 或 Dask（用于并行处理多台机器上的大型数据集的框架）用于处理非常大的数据
- 用于中等数据的工作队列，例如 Celery（对于 Python）或 BullMQ（对于 Node.js）
- 针对小数据的简单脚本

我们还处理重新嵌入向量：

- 当源文档更改时，我们重新嵌入更改后的文本块。
- 当我们更改嵌入模型时，我们重新嵌入了所有内容。

好的嵌入向量管道是增量的。它只处理新的或更改的内容，而不是每次处理整个数据集。

## 选择嵌入模型 {#choosing-an-embedding-model}

现在，让我们选择正确的嵌入模型。 嵌入模型决定了我们检索的质量。糟糕的嵌入模型意味着即使是最好的向量 DB也会返回垃圾。 2026 年常见生产方案：

- **Voyage AI（Voyage 4 Large）：** 目前在英语 RAG 质量排行榜上名列前茅。使用混合专家模型 (MoE) 架构，使服务成本显着低于同类密集模型。当检索质量比成本更重要时，大多数认真的 RAG 团队都会转向 Voyage。
- **OpenAI（文本-嵌入向量-3-小/3-大）：** 便宜、简单，对于大多数应用程序来说足够好。 text-嵌入向量-3-small 是主要提供商提供的最便宜的可行选择，每百万 token 为 0.02 美元。
- **Cohere (embed-v4):** 跨 100 多种语言的强大多语言支持。现在是多模态（文本+图像），因此我们可以将文本和图像嵌入到同一空间中。具有任务类型的嵌入向量（搜索查询、搜索文档、分类、聚类），可让我们针对特定任务进行优化。还支持开箱即用的俄罗斯套娃尺寸。
- **Gemini Embedding 2：** 原生支持多模态，文本、图像、视频、音频和 PDF 都映射到共享嵌入空间。质量高、定价合理，默认维度为 3072，支持截断为 768 或 1536 维。
- **BGE / Jina（开源）：** 当我们想要自托管或关心数据隐私时。 BGE-M3 和 Jina v5 是热门选择。

## 俄罗斯套娃嵌入向量 {#matryoshka-embeddings}

一个值得了解的有用技巧。 **Matryoshka 嵌入向量** 经过训练，这样我们就可以将它们截断到更小的维度，而无需重新训练。因此，我们可以存储完整的 3072 维嵌入向量一次，但在查询时仅使用前 256 或 512 维进行快速首次搜索，然后使用完整向量重新排名。

这为我们提供了内存与质量的旋钮，而无需维护两个嵌入模型。 OpenAI text-嵌入向量-3 和 Cohere 都支持这一点。

一个好的规则：根据任务类型、语言、预算和隐私需求选择嵌入模型。切换嵌入模型意味着重新嵌入向量一切，因此这个决定具有重力。
