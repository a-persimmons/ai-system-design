# RAG（检索增强生成） {#rag-retrieval-augmented-generation}

LLM 不知道我们公司的数据。他们接受了带有截止日期的公共数据训练。

如果用户问我们的聊天机器人“我们商店的退款政策是什么？”，LLM 不知道。

为了解决这个问题，我们使用 **RAG (检索增强生成)** 。

**RAG = 检索 + 增强 + 生成。** 的想法很简单：

1. **检索：** 使用向量搜索查找我们的私人数据的相关部分。
2. **增强：** 将这些片段作为上下文添加到提示词中。
3. **生成：** 让 LLM 使用该上下文生成答案。

我们有一篇关于 [RAG 如何工作？](https://outcomeschool.com/blog/retrieval-augmented-generation-rag) 的详细博客，逐步解释了完整流程。

让我们看看流程。

**第 1 步：索引（离线，完成一次）**

- 我们获取所有文档（PDF、网页、知识库）。
- 我们将它们文本块分成更小的部分（比如每个 500 个 token）。
- 我们使用嵌入模型计算每个文本块的嵌入向量。
- 我们将所有这些嵌入向量与原始文本一起存储在向量数据库中。

**第2步：查询时间（在线，为每个用户查询完成）**

- 用户询问“退款政策是什么？”
- 我们计算问题的嵌入向量。
- 我们在向量数据库中搜索前 5 个最相似的文本块。
- 我们将这些文本块放入提示词中：“这里有一些上下文。根据此回答。上下文：[chunks]。问题：退款政策是什么？”
- 我们将其发送至 LLM。
- LLM 根据我们的私人背景给出了答案。

该架构如下所示：

```
Indexing (offline)
Documents -> Chunker -> Embedding Model -> Vector DB

Query (online)
User -> Backend -> Embedding Model -> Vector DB (top-k chunks)
                                              |
                                              v
                       LLM <- (Prompt + chunks)
                        |
                        v
                     Response
```

思考 RAG 的最佳方式是与现实世界进行类比。假设我们想在一个大图书馆中找到答案。 **标准 RAG 就像图书管理员取一本书。** 我们把问题交给我们。图书管理员挑选出与单词最匹配的书，交给我们，LLM 读取它并写出答案。一枪。完毕。

馆员流动速度快，但无法适应问题。对于需要许多步骤的更复杂的问题，我们需要一名研究人员而不是图书馆员。即 **[Agentic RAG](https://outcomeschool.com/blog/agentic-rag)** ，其中 [AI 智能体](https://outcomeschool.com/blog/ai-agent) 驱动检索过程并决定每一步。我们将在下面详细看到Agentic RAG。

RAG 是当今人工智能产品最流行的架构。 ChatGPT 搜索、Perplexity、客户支持机器人、代码助理 - 所有这些都以某种形式使用 RAG。

## 文档解析和摄取 {#document-parsing-and-ingestion}

现在，我们来讨论大多数 RAG 教程都会跳过的部分：从现实文档中获取干净的文本。在生产中，我们的源数据很少是干净的 Markdown。它是 PDF、扫描图像、幻灯片、网页、电子表格、Word 文档和电子邮件。

如果我们将杂乱的文本输入管道中，再多巧妙的检索也无法拯救我们。该模型只能根据给出的内容进行回答。

真实的文档解析管道执行以下操作：

- **格式检测：** 找出这是什么类型的文件（PDF、图像、HTML、DOCX、音频等）。
- **布局感知解析：** 保留标题、列表、列和阅读顺序。简单地扁平化的两列 PDF 变得毫无意义。
- **OCR（光学字符识别）：** 对于扫描的 PDF 和图像，将像素转换为文本。质量取决于图像清晰度、字体、语言和倾斜，因此预处理（倾斜校正、去噪）与 OCR 引擎一样重要。
- **表提取：** 表是最难的部分。我们希望保留单元格边界和标题，通常会发出 HTML 或行/列模型，而不是将表格扁平化为散文。表格通常承载着最有价值的数据，因此这一步至关重要。
- **图像和图形处理：** 标题图像，运行视觉模型来描述图表，将图像存储在 blob 存储中，并从文本块链接它。
- **元数据丰富：** 添加文档标题、作者、日期、源 URL、页码、章节标题。该元数据将成为稍后检索的过滤器。

常见的模式是 **基于置信度的路由** ：高置信度解析直接通过，中等置信度被标记进行抽查，低置信度进入手动审查。

可用工具包括：Unstructured、LlamaParse、Mistral OCR、Nemotron Doc Pipeline、AWS Textract 和 Azure Document Intelligence。

在实际的 RAG 项目中，60% 到 80% 的工程工作都投入到此步骤中。我们必须像对待 LLM 调用本身一样小心地构建文档管道。

## 分块策略 {#chunking-strategies}

文档如何切分为文本块，决定了 RAG 的质量。**文本块（chunk）** 是从较大文档中切出的一小段文本。详细文章 [RAG 的分块策略](https://outcomeschool.com/blog/chunking-strategies-for-rag) 通过实例解释各种策略。

如果文本块太大，LLM 会产生太多噪音。如果文本块太小，我们就会失去上下文，并且文本块本身没有意义。

常见的分块策略：

- **固定大小分块：** 每 500 个 token 进行切割。简单但中间断句。
- **基于句子的分块：** 在句子边界处剪切。更适合自然阅读。
- **递归分块：** 尝试先切大断点（段落），然后切中断点（句子），然后切断小断点（单词）。
- **语义分块：** 使用嵌入向量检测主题转移并切入那里。质量最好但速度最慢。
- **文档结构分块：** 对于代码，在函数边界处进行切割。对于降价，请剪切标题。

**文本块重叠** 意味着我们在下一个文本块的开头重复一个文本块的最后几行，这样边界处的想法在至少一个文本块中仍然显得完整。常见的设置是与文本块尺寸重叠约 10% 至 20%。因此，对于 500 个 token 的文本块，50 到 100 个 token 的重叠效果很好。

正确的文本块大小取决于答案的类型：

- **简短而真实的答案** （常见问题解答页面，产品目录）：大约200至300个token的小型文本块。
- **说明和程序** （政策手册、技术文档）：约500至800个token的中型文本块。对于大多数项目来说，这是安全的默认设置。
- **长推理和叙述** （研究论文、法律合同、会议笔录）：较大的文本块，约为1000至1500个token。

我们从默认值开始，然后根据我们自己的数据进行评估来调整它。

即使分块做得很好，文本块仍可能丢失上下文。例如，“收入比上一季度增长了 3%”并未说明是哪家公司、哪个季度。为此，可以采用 **上下文检索（Contextual Retrieval）** ：存储每个文本块之前，让 LLM 写一段简短说明，解释文本块的来源；计算嵌入向量和构建 BM25 索引前，将这段说明加到文本块中。我们有一篇详细文章：[上下文检索如何工作？](https://outcomeschool.com/blog/how-does-contextual-retrieval-work)

## 混合搜索 {#hybrid-search}

向量搜索擅长理解含义，但不擅长“订单 ID 12345”或“第 4.2.1 节”这类精确匹配查询。

对于精确匹配，旧的关键字搜索（ **BM25** - 最佳匹配 25）要好得多。

因此，生产环境的 RAG 会使用 [**混合搜索**](https://outcomeschool.com/blog/how-does-hybrid-search-work)：同时运行向量搜索和 BM25，融合得分，返回两者中最好的结果。

两个结果列表的分数尺度不同，不能直接相加。常见融合方式是 **倒数排名融合（RRF）** ：忽略原始得分，只使用每个文本块在各列表中的排名。在两个列表中都排名靠前的文本块，最终会排到前面。

Elasticsearch、OpenSearch、Weaviate 和 Qdrant 等工具原生支持混合搜索。

## 使用 HyDE 进行查询转换 {#query-transformation-with-hyde}

检索还有一个问题：用户问题与真实答案的形式通常很不一样。问题简短，呈疑问句形式；文档里的答案较长，呈陈述形式。因此，它们的嵌入向量不一定彼此接近。

这时，[**HyDE**](https://outcomeschool.com/blog/how-does-hyde-work) 就派上了用场。

**HyDE 是 Hypothetical Document Embeddings（假设性文档嵌入）的缩写。它先让 AI 模型为问题编写一个假设答案，再用这个假设答案进行搜索，而不是直接搜索问题。**

HyDE = 假设性 + 文档 + 嵌入。核心思想很简单：答案与答案在形式上更接近。因此，要找到真实答案，可以先用一个看起来像答案的文本进行搜索。

这个假设答案不会展示给用户，也不假定它是正确的。我们只是把它用作更好的检索线索，最终答案仍然依据真实文档生成。

为了便于理解，假设相近程度用 0 到 1 表示：

- 问题嵌入向量与真实答案文本块相比：紧密度为 0.55。
- 假设答案的嵌入向量与真实答案文本块相比，相近程度为 0.88。

在这里，我们可以注意到假答案更接近真实答案，因此搜索更容易选择正确的文本块。

**优点：** 文本块对于简短、模糊或技术问题更好，无需额外训练。

**缺点：** 一个额外的LLM调用，这意味着更多的延迟和更多的成本。虚假的答案也可能偏离主题。

一个好的做法是在同一组问题上测试普通搜索和 HyDE，并保留为我们的数据找到更好的文本块的问题。

HyDE 并不是转换查询的唯一办法。采用 **查询改写（Query Rewriting）** 时，LLM 会在检索前把用户问题改写为清晰、独立的搜索查询，对追问和模糊问题尤其有帮助。采用 **多查询检索（Multi-Query Retrieval）** 时，LLM 从不同角度生成问题的多个版本，分别搜索，再通过倒数排名融合（RRF）合并结果。我们有一篇详细文章：[查询改写与多查询检索如何工作？](https://outcomeschool.com/blog/how-do-query-rewriting-and-multi-query-retrieval-work)

## 重排序 {#reranking}

初次检索速度快，但准确性有限。例如先取回排名前 50 的文本块，再用一个较小、较慢但十分准确的 [**重排序模型（reranker）**](https://outcomeschool.com/blog/how-does-a-reranker-work) 重新为这 50 个文本块打分，只保留前 5 个。

重排序模型通常采用 **交叉编码器（cross-encoder）** 。它与普通向量搜索的区别很简单：向量搜索分别编码问题与文本块，再比较两个向量，速度快但理解较浅；交叉编码器将问题和文本块一起输入模型，输出一个相关性分数。后者速度较慢，但模型可以直接比较问题与文本块中的词，因此准确性高得多。

这个两阶段筛选流程如下：

```
              User Question
                   |
                   v
      +---------------------------+
      |  Stage 1: Retrieval       |
      |  (vector + BM25)          |
      |  Fast, cheap, ~ok recall  |
      +-------------+-------------+
                    |
                    | top 50 chunks
                    v
      +---------------------------+
      |  Stage 2: Reranker        |
      |  (cross-encoder model)    |
      |  Slower, very accurate    |
      +-------------+-------------+
                    |
                    | top 5 chunks
                    v
                   LLM
```

这种两阶段检索——低成本检索加准确重排序——是高质量 RAG 的标准做法。第一阶段以低成本广泛召回，第二阶段精确选出最合适的结果。

重排序模型的例子包括 Cohere Rerank、BGE Reranker 和 Jina Reranker。

加入重排序模型是显著改善 RAG 质量的最简单改动之一。它还可以缓解稍后会介绍的“中间信息遗失”问题，因为发送 5 个优质文本块，胜过发送 50 个普通文本块。

## ColBERT 与后期交互 {#colbert-and-late-interaction}

接下来便有一个问题：交叉编码器重排序准确但慢；向量搜索快却较粗糙，因为它将整段文字压缩为一个向量，丢失了词级细节。能否兼得两者的优点？

[**ColBERT**](https://outcomeschool.com/blog/decoding-colbert) 就是为此而来。它为 **每个 token 保留一个向量** ，而非每段文字只有一个向量，再通过低成本的 **后期交互（late interaction）** 步骤完成匹配。

```
  1. Cross-encoder  (accurate, slow)

     query + document together  ->  BERT  ->  score
     BERT runs once per pair, nothing can be stored ahead of time


  2. Single-vector dual encoder  (fast, blunt)

     query     ->  BERT  ->  [ one vector ]
                                          >--  one dot product  ->  score
     document  ->  BERT  ->  [ one vector ]


  3. Late interaction, ColBERT  (accurate and fast)

     query     ->  BERT  ->  [ v1  v2  v3 ]
                                          >--  MaxSim  ->  score
     document  ->  BERT  ->  [ v1  v2  v3  v4  v5 ]
```

这里可以清楚地看到区别。文档编码时不需要知道查询内容，因此每个文档的向量都能提前离线计算一次。查询时，每个查询 token 找出与自己最匹配的文档 token，这称为 **MaxSim** ，然后将这些分数相加。

代价是存储空间。一段 100 token 的文字需要 100 个向量，而不是 1 个，存储量增加到 100 倍。也就是说，ColBERT 用磁盘空间换取准确性。它适合作为强力重排序模型，或在质量比存储成本更重要时用于端到端检索。

## Agentic RAG（智能体驱动的 RAG） {#agentic-rag}

标准 RAG 可以处理简单问题，但问题一复杂，它就容易失效。这位“图书管理员”只会匹配词语，不会思考，不会追问，也无法决定应该去哪里查找。

标准 RAG 在以下情况下会失败：

- **多跳问题：** “2023年收购Acme的公司第四季度收入是多少？” - 一次检索无法回答这个问题。
- **模糊查询：** “新政策怎么样？” - 系统不知道哪个策略。
- **多个数据源：** 有些问题需要SQL数据库，有些需要向量存储，有些需要实时网络搜索。
- **不良检索质量：** 检索到的最靠前的文本块不相关。标准 RAG 不知道这一点，只是将它们传递给 LLM。

因此，[**Agentic RAG**](https://outcomeschool.com/blog/agentic-rag) 来救援。我们用研究员取代图书馆员。

简单来说：

**Agentic RAG = RAG + 控制检索步骤的 AI 智能体。**

在Agentic RAG中，智能体决定每一步：

- 这个问题还需要检索吗？
- 我们应该使用哪种工具或数据源？
- 搜索查询应该是什么样子？
- 检索到的文本块是否足以回答？
- 我们应该用更好的查询再次检索吗？
- 我们应该结合多个来源的结果吗？
- 我们什么时候才能停下来写下最终的答案呢？

Agentic RAG 循环：

```
User Question
     |
     v
+------------------+
|    AI Agent      |
|   (the LLM)      |
+------------------+
     |
     | thinks: "Do I need to retrieve?
     |          Which tool? What query?"
     v
+------------------+
|  Retrieval Tool  |
|  (vector / SQL / |
|   web / graph)   |
+------------------+
     |
     | returns chunks
     v
+------------------+
|    AI Agent      |
|   evaluates:     |
|  "Good enough?"  |
+------------------+
     |
     +--- No  --> retrieve again with a new query
     |
     +--- Yes --> generate the final answer
```

Agentic RAG 的常见模式： **[ReAct 式 RAG](https://outcomeschool.com/blog/react-agent)** （思考、行动、观察循环）、 **Self-RAG** （智能体对自己的检索进行评分），以及 **Corrective RAG (CRAG)** （当主检索不良时，智能体推荐使用降级回退源）。

权衡是真实的：Agentic RAG 具有更高的延迟、更高的成本，并且更难调试。仅当标准 RAG 无法完成这项工作时，我们才使用 Agentic RAG。

让我将标准 RAG 和 Agentic RAG 之间的差异制成表格，以便您更好地理解，以便您可以根据您的用例决定使用哪一种。

| 比较项 | 标准 RAG | Agentic RAG |
| --------------------------------- | --------------------------- | --------------------------------- |
| 执行流程 | 固定流水线 | 动态循环 |
| 检索数量 | 1 个 | 多个，根据需要 |
| 使用的工具 | 一个（通常是向量搜索） | 许多（向量、SQL、Web 等） |
| 查询重写 | 否 | 是 |
| 检查检索文本块的质量 | 否 | 是 |
| 多跳问题 | 无法处理 | 可以处理 |
| 延迟 | 低 | 较高 |
| 成本 | 低 | 较高 |
| 构建复杂性 | 简单 | 更复杂 |

## GraphRAG {#graphrag}

现在，让我们转向更高级的 RAG 形式。当答案就在文本块中时，向量 RAG 就非常有用。当答案需要连接许多文本块的事实时，它会很困难。对于“这两个人有什么联系？”之类的问题。或者“哪些政策适用于该类别中的所有产品？”，向量搜索仅提取一些相关的文本块，而 LLM 必须猜测其中的联系。

因此，[**GraphRAG**](https://outcomeschool.com/blog/graphrag) 来救援。它通过首先从语料库构建 **知识图** 来解决这个问题。

简单来说：

**[GraphRAG](https://outcomeschool.com/blog/graphrag) = 知识图谱 + RAG。检索关系，而不仅仅是文本块.**

该流程有两个阶段。

**阶段 1：索引（离线）**

- 阅读每一份文件。
- 使用 LLM 提取 **实体** （人、产品、地点、概念）和 **关系** （谁为谁工作，什么是什么的一部分）。
- 将它们与原始文本文本块一起存储在图形数据库（Neo4j、Memgraph）中。
- （可选）将实体分组到 **社区** 并生成社区摘要。

**阶段 2：查询时间**

- 用户提出问题。
- 我们提取问题中提到的实体。
- 我们遍历该图以查找相关实体、路径和社区摘要。
- 我们将这些（加上相关文本文本块）传递给 LLM 作为上下文。

从语料库中提取的知识图的一个小示例如下所示：

```
                +-----------+
                | Jane Doe  |
                +-----------+
                      |
                      | is_CEO_of
                      v
                +-----------+      acquires       +-----------+
                |  Globex   | -----------------> |   Acme    |
                |           |     (in 2023)      +-----------+
                +-----------+
                      |
                      | has_report
                      v
                +-----------+
                | Q4 2023   |
                | revenue   |
                +-----------+

Question: "Q4 revenue of the company that acquired Acme in 2023?"
Traversal: Acme <- (acquires) <- Globex -> (has_report) -> Q4 2023 revenue
```

这些箭头以主动关系表示：Globex `acquires` Acme，Globex `has_report` 2023 年第四季度收入，Jane Doe `is_CEO_of` Globex。回答问题时，从 Acme 沿 `acquires` 边 **反向** 遍历，得到 Globex，再沿 `has_report` 边 **正向** 遍历，得到 2023 年第四季度收入。

向量 RAG 永远不会在单次检索中建立此连接。 GraphRAG 遍历边缘并通过遵循关系找到答案。

GraphRAG 更擅长：

- 多跳问题（“收购 Acme 的公司第四季度的收入是多少？”）
- 整体摘要（“该数据集中的主要主题是什么？”）
- 以实体为中心的查询（“向我显示与客户 X 相关的所有内容”）

权衡：GraphRAG 的索引成本要高得多（每个文档都要经过 LLM 提取）并且更难以增量更新。当关系很重要且数据相当稳定时，我们会使用它。

Microsoft Research 的 GraphRAG 项目是最著名的实现。其他工具：LlamaIndex 知识图索引、Neo4j LLM 图形生成器。

简而言之：

- **向量 RAG** 最适合“找到谈论 X 的文本块”。
- **GraphRAG** 最适合“解释 X、Y 和 Z 是如何连接的”。

在生产中，两者经常一起使用。

## 无向量RAG {#vectorless-rag}

现在，让我们看看相反的方向。 向量 RAG 有一些实际问题：

- **Chunking 打破了这个意义。** “牙科治疗承保”可以落地在一个文本块中，而“第 3 章中的所有治疗仅在等待一年后才适用”在另一个文本块中。系统选择第一个，并给出一个肯定错误的答案。
- **相似与正确不一样。** 在“哪些政策 **不** 涵盖牙科治疗？”中，微小的“不”字几乎没有移动数字。
- **特殊单词和数字受到影响。** `Clause 14.2.b` 和 `Clause 14.3.b` 看起来几乎与嵌入模型相同。
- **我们无法解释结果。** 当选择了错误的文本块时，向量数据库无法告诉我们原因。

因此，[**无向量 RAG**](https://outcomeschool.com/blog/vectorless-rag) 来救援。

**无向量 RAG = 没有向量的 RAG。** 我们不是通过数字相似性进行搜索，而是让 LLM 本身查看文档的结构并决定打开哪一部分，这正是人类在书中找到答案的方式。

假设我们购买了一台洗衣机并想了解保修情况。我们得到了一本 200 页的手册。我们不衡量任何事物的相似性。我们打开目录，看到“第9章：保修和服务”，跳到第154页，阅读它。这就是整个想法。

它分两个阶段工作：

- **准备文档：** 我们根据文档构建一棵树，这与目录相同。对于每个节点，我们存储标题、一两行摘要以及真实文本的位置。我们不削减任何东西。
- **回答问题：** 我们仅显示 LLM 树的顶层，并询问哪些章节可以包含答案。我们只打开那些章节并再次询问。我们继续向下，一层一层（这称为 **树搜索** ），直到到达正确的部分。然后，我们将这些部分的全文发送到 LLM 以编写最终答案及其使用的部分编号。

让我将向量 RAG 和无向量 RAG 之间的差异制成表格，以便您更好地理解，以便您可以根据您的用例决定使用哪一种。

| 向量 RAG | 无向量 RAG |
| -------------------------------------------------- | ------------------------------------------------------ |
| 需要嵌入模型和向量数据库。 | 两者都不需要。 |
| 文档被切成固定尺寸文本块。 | 文件保持完整并逐节阅读。 |
| 通过测量数字之间的距离进行搜索。 | 按 LLM 阅读标题和摘要进行搜索。 |
| 搜索期间没有推理。 | 在搜索的每一步进行推理。 |
| 每个问题都非常快且非常便宜。 | 速度较慢且成本较高，因为它需要几次 LLM 调用。 |
| 很难解释为什么选择文本块。 | 很容易解释，因为 LLM 给出了它的理由。 |
| 可以很好地扩展到数百万个文档。 | 最适合处理长且结构良好的文档。 |
| 难以处理精确代码、数字和否定表达。 | 能较好地处理精确代码、数字和否定表达。 |

我们必须将 **向量 RAG** 用于速度和低成本至关重要的大量短文档，例如包含一百万篇文章的帮助中心。我们必须使用 **无向量 RAG** 来处理冗长、结构良好的文档，其中错误答案的成本很高，例如保险单、法律合同、年度报告和技术手册。许多强大的系统都使用这两种方法：廉价的向量或关键字搜索将数百万个文档缩小到二十个，然后树搜索找到这二十个文档中的确切部分。
