# AI 网关 {#ai-gateway}

在实际生产中，我们的应用程序不会直接调用 OpenAI、Anthropic 或我们自托管的 vLLM。我们在中间放置一个单层，称为 **AI 网关** （也称为 LLM 网关）。我强烈建议将 AI 网关作为首先构建的基础设施之一，因为一旦我们拥有它，其他所有问题（成本、速率限制、缓存、防护机制、可观测性）都会变得容易得多。

简而言之， **an AI网关是专门针对LLM流量的反向代理。**

常规 API 网关路由 HTTP 请求。 AI 网关还了解 token、提示词、流媒体和成本。这是我们公司的每个 LLM 呼叫都经过的单点。

典型的 AI 网关如下所示：

```
+--------+         +-------------+         +-------------------+
|  App   | ------> | AI Gateway  | ------> | OpenAI / Claude   |
+--------+         |             | ------> | Gemini / Llama    |
                   |             | ------> | Self-hosted vLLM  |
                   +-------------+         +-------------------+
```

AI网关给我们带来了什么？

- **单端点，多种模型：** 我们的应用程序使用标准架构调用一个 URL。网关确定将其发送到哪个提供商和模型。从 GPT-5.5 切换到 Claude Opus 4.8 是配置更改，而不是代码更改。
- **多提供商故障转移：** 如果 OpenAI 宕机，网关会在我们的应用程序不知情的情况下回退到 Anthropic。
- **集中成本跟踪：** 每个呼叫都标记有用户、团队、功能和请求 ID。成本仪表板变得微不足道。
- **集中速率限制和配额：** 所有多维速率限制（TPM、RPM、并发、基于成本）都位于此处，而不是在每个微服务中。
- **集中缓存：** 提示词缓存和语义缓存在网关内部运行。
- **集中式防护机制:** 输入和输出防护机制作为网关策略运行。一个加强整个公司安全的地方。
- **审核日志：** 每个提示词和响应都会被记录下来，以进行调试和合规性。
- **可观测性:** 延迟、token 使用情况、错误、缓存命中率 - 全部集中在一个仪表板中。

使用的工具：Portkey、LiteLLM、Kong AI Gateway、Envoy AI Gateway、TrueFoundry、AWS Bedrock（也充当网关）。

在设计AI 网关时，我们必须做好以下几点：

- **直通流式传输：** 流式传输必须无缓冲地流过。在发送之前缓冲完整响应的幼稚网关会破坏 SSE 体验。 token 计数是从最终 SSE 事件记录的。
- **低网关延迟：** 网关会增加每次调用的开销。我们希望此开销低于 10 毫秒。
- **断路器：** 如果网关本身不健康，应用程序应回退到直接调用模型提供者。
- **多区域部署：** 为了低延迟和可靠性，我们在多个区域部署网关，并将用户路由到最近的区域。

一旦我们有了AI 网关，这个博客中的所有其他问题（速率限制、成本、缓存、防护机制、可观测性）都会有一个家。这就是为什么AI 网关是任何认真的人工智能团队构建的首要基础设施之一。
