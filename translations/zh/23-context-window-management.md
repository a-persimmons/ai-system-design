# 上下文窗口管理 {#context-window-management}

每个 LLM 都有一个最大 [上下文窗口](https://outcomeschool.com/blog/context-window)。 GPT-5.5 具有高达 400k token。 Claude Sonnet 4.6 和 Opus 4.8 的 token 高达 100 万张。有些模型甚至更进一步。但它们都是有限的。

在生产中，我们总是遇到上下文限制：

- 长时间的聊天已经超出了限制。
- RAG 系统检索到太多文本块。
- 智能体循环累积了太多工具结果。

但还有一个更深层次的问题。最大上下文窗口是我们_允许_使用的大小，而不是我们必须使用的大小。

## 上下文腐化、中间信息遗失和 RoPE 衰减 {#context-rot-lost-in-the-middle-and-rope-decay}

当我们用更多的 token 填充上下文时，会发生三件事，它们都会损害质量。

**1。 上下文腐化.** 随着上下文中 token 数量的增长，模型从该上下文中的任何位置调用信息的能力会下降。长上下文评估（例如 **Needle-in-a-Haystack** 风格测试以及更新的 RULER 和 LongBench 基准）表明，即使是宣传很长上下文窗口的模型，在达到该限制之前就开始失去准确性。因此，大的广告环境并不意味着同样大的有效环境。

**2。 [迷失在中间](https://outcomeschool.com/blog/lost-in-the-middle-problem-in-llms).** Liu等人的研究。 （2023）表明模型最关注上下文的开始和结束，而最不关注中间。如果我们根据事实的位置绘制准确性，我们会得到一条 U 形曲线。因此，放置在长上下文中间的关键事实比放置在顶部或底部的相同事实更有可能被忽略。这会默默地破坏将 50 个文本块转储到提示词的 RAG 系统。解决方法是发送较少的内容，但发送正确的内容（使用重排序模型并保留前几个文本块），并将最相关的文本块放在开头和结尾。

**3. RoPE 位置衰减。** 现代 LLM 使用 [**旋转位置嵌入（RoPE）**](https://outcomeschool.com/blog/math-behind-rope-rotary-position-embedding) 编码每个 token 的位置。RoPE 使两个 token 之间的注意力分数只依赖其相对距离；两者越远，注意力通常越弱。较新的模型缓解了这一问题，但还没有生产模型完全消除它。

实际意义：我们在提示词中放置信息的位置与信息本身一样重要。重要的上下文应该放在系统提示词的顶部或问题的旁边，而不是埋在中间。

## 上下文工程 {#context-engineering}

现在，我们来了解一下上下文工程。由于这些影响，出现了[**上下文工程**](https://outcomeschool.com/blog/context-engineering)的纪律。

**上下文工程是设计、组织和管理进入 LLM 上下文窗口的所有内容的实践，以便模型能够可靠地完成其任务。**

它是[提示工程](https://outcomeschool.com/blog/prompt-engineering)上面的下一层。 提示词工程是关于一条指令的写法。 上下文工程涉及模型看到的所有内容：系统提示词、检索到的文本块、工具定义、工具结果、内存和对话历史记录。 上下文工程决定：

- 包含哪些信息
- 排除哪些信息
- 每个部件的放置位置（顶部、中间、底部）
- 如何总结或压缩旧信息
- 如何构建上下文以便模型能够找到它需要的内容

思考这个问题的一个有用的方法是：上下文窗口是一个小的工作区，我们是决定它发生什么的人。我们选择放入什么、省略什么、将什么放在顶部以及将什么推到底部。该模型只能看到我们放置在那里的内容。

我们需要一个策略来管理上下文窗口。

## 截断 {#truncation}

当我们即将溢出时，删除最旧的消息。简单但丢失信息。

## 总结 {#summarization}

当对话很长时，将较旧的消息总结为较短的摘要，并将该摘要放入提示词中。这就是大多数聊天产品所做的。

## 滑动窗口 {#sliding-window}

仅保留最后 N 条消息和系统提示词。忘记中间的一切。适用于只有最近上下文很重要的聊天。同样的想法也存在于某些模型中，其中每个 token 仅关注最近 token 的固定窗口。我们有一篇关于 [滑动窗口注意力机制如何工作的详细博客](https://outcomeschool.com/blog/how-does-sliding-window-attention-work)。

## 上下文压缩 {#compaction}

[**上下文压缩**](https://outcomeschool.com/blog/how-does-context-compaction-work) 是将旧对话缩小为简短摘要的技术，因此在上下文窗口再次获得可用空间时，重要事实会保留下来。对于智能体循环，我们还压缩了不再需要的工具结果。保留问题、决定和重要发现。删除详细的工具输出。良好的压缩永远不会概括系统指令、用户的主要目标或最新消息。只有凌乱的中间部分被压缩。例如，一个小时的编码智能体的工作可以变成一个简短的说明，例如“目标：修复登录错误。已经更改了`auth.py`和`login.py`。测试正在通过。”这就是智能体如何在不丢失情节的情况下完成数小时的长时间任务。

## 分层内存 {#hierarchical-memory}

将完整历史记录存储在向量数据库中，并仅在需要时检索相关部分。

选择正确的策略取决于用例。对于聊天来说，总结效果很好。对于智能体，压缩效果很好。对于问答来说，分层记忆效果很好。
