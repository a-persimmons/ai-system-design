# 如何解决 AI 系统设计问题 {#how-to-solve-any-ai-system-design-problem}

现在我们已经了解了所有构建块，让我们看看如何将它们组合在一起来解决任何 AI 系统设计问题。

在 AI 系统设计面试过程中，我们必须遵循以下 8 个步骤：

1. 要求
2. 人工智能目标
3. 数据准备
4. 建筑设计
5. 模型选择和提示
6. 评价
7. 部署和服务
8. 监控

让我们以客户支持聊天机器人为例，详细讨论每个步骤。

**问题陈述：** 为 SaaS 公司的客户支持聊天机器人设计AI 系统。

## 第 1 步：要求 {#step-1-requirements}

此步骤的主要目标是清楚地理解问题和需求。

在开始解决问题之前，充分理解问题陈述至关重要，因此我们需要向面试官提出一些澄清问题。

以下是客户支持聊天机器人的一些澄清问题：

**候选：** 用户会问什么样的问题？
**采访者：** 主要是产品使用、计费和帐户相关的问题。

**C候选：** 我们必须支持多种语言吗？
**采访者：** 现在，我们只考虑一种语言，英语。

**候选：** 预期规模是多少？
**采访者：** 10万用户，每天5万条聊天，每次聊天大约5条消息。

**C候选：** 延迟预期是多少？
**采访者：** 第一个token应该在1秒内出现。

**候选人：** 每月预算是多少？
**采访者：** 每月 5000 美元。

**C候选人：** 我们可以访问公司的文档吗？
**采访者：** 是的，我们有一个帮助中心，里面有大约 500 篇文章。

**候选人：** 机器人应该只回答问题，还是也采取取消订阅等操作？
**采访者：** 现在只回答问题。没有任何动作。

**C候选人：** 当机器人不知道答案时应该做什么？
**采访者：** 升级为人工支持智能体。

**C候选人：** 我们是否有权访问用户和人类智能体之间过去的对话？
**采访者：** 是的，我们有过去一年的聊天记录。

所以，现在我们有了一个清晰的画面。下一步是定义人工智能目标。

## 第 2 步：AI 目标 {#step-2-ai-objective}

在此步骤中，我们需要定义 AI 目标。

对于我们的示例，客户支持聊天机器人的目标是根据公司的帮助中心对用户的问题给出合理的答案，或者如果机器人不自信，则升级为人类智能体。

- **输入：** 用户问题和对话历史记录。
- **输出：** 基于公司帮助中心、具有事实依据的答案，或者“转人工”的信号。

这是一个关于私有数据的问答问题。所以正确的模式是 RAG (检索增强生成)。

下一步是数据准备。

## 第三步：数据准备 {#step-3-data-preparation}

在这里，我们讨论我们需要的数据以及我们必须做的任何数据清理。

对于我们的示例，我们将具有以下内容：

- **帮助中心文章：** 500篇文章，约20万字。这是事实的主要来源。我们将在向量数据库中对它们进行索引。
- **过去的聊天对话：** 1 年人工支持聊天。用于评估（测试机器人是否正确回答）和查找常见问题。
- **用户和帐户数据：** 从主数据库中提取。用于个性化答案，例如“您当前的计划是......”。
- **Eval 集：** 200 个精选问题及预期答案。用于每次我们更改某些内容时测试系统。

我们还进行数据清理：

- 删除旧的、已弃用的文章。
- 从文章中去除 HTML、广告和导航。
- 规范格式和标题。
- 使用之前从过去的对话中删除个人身份信息 (PII)。

下一步是架构设计。

## 第四步：架构设计 {#step-4-architecture-design}

这一步是讨论的核心。

对于我们的客户支持聊天机器人，其架构如下所示：

```
User -> Backend -> Embedding Model -> Vector DB (top 50 chunks)
                                              |
                                              v
                                      Reranker (top 5 chunks)
                                              |
                                              v
                          LLM (system prompt + chunks + question)
                                              |
                                              v
                                       Streamed Response
```

组件：

- **分块器：** 递归分块，每个文本块 500 个 token 和 50 个 token 重叠。
- **嵌入模型:** 小型、快速的嵌入模型。
- **Vector DB：** PostgreSQL 与 pgvector。我们不需要这种规模的专用向量数据库。
- **混合搜索：** 将向量搜索与BM25关键字搜索相结合。
- **重排序模型:** Cohere Rerank 或 BGE 重排序模型从前 50 名中挑选前 5 名。
- **LLM:** 用于大多数查询的小型聊天模型。使用模型路由将更难的查询路由到更大的模型。
- **Caching：** 提示词缓存为系统提示词。 语义缓存用于重复问题。
- **Streaming：** SSE 用于聊天 UI。
- **Storage：** PostgreSQL，用于用户、对话和反馈。 嵌入向量的 pgvector。
- **异步处理：** 此处没有长时间运行的任务。一切都是实时的。

现在是讨论模型选择和提示的时候了。

## 第5步：模型选择和提示 {#step-5-model-selection-and-prompting}

在这里，我们选择 LLM、嵌入模型和重排序模型。我们还编写了系统提示词。

模型选择：

- **主聊天模型：** Haiku 4.5，成本低、速度快，足以处理 90% 的查询。
- **降级回退聊天模型：** Sonnet 4.6，用于硬查询（当主模型说“我不知道”时）。
- **嵌入模型:** 小型、便宜的模型。对于这种规模，我们不需要最大的嵌入模型。
- **重排序模型：** 一致性重新排名。

系统提示词模板：

```
You are a customer support assistant for [Company].
Use only the context below to answer the user's question.
If the context does not have the answer, reply with
"I do not know" and suggest the user contact human support.
Do not make up facts.

Context:
{chunks}

Question:
{user_question}
```

提示词-工程选择：

- “只使用上下文”要求答案以提供的资料为依据，从而减少幻觉。
- “如果上下文没有答案，请回答‘我不知道’”可以减少编造答案并引发升级。
- 系统提示词在所有请求中都是恒定的，因此我们对其使用提示词缓存。

下一步是评估。

## 第6步：评估 {#step-6-evaluation}

在上线之前，我们会根据 200 个精心挑选的问题对系统进行测试。

使用的评估技术：

- **LLM 评审:** 使用更强的模型将机器人的答案与预期答案进行比较。
- **忠实性检查：** 使用 Ragas 检查答案是否基于检索到的上下文。
- **拒绝准确度：** 机器人在应该知道的情况下多久说一次“我不知道”？当它应该拒绝时，它多久会回应一次？
- **检索质量：** 前 5 个文本块实际上是否适合该问题？
- **人类评估：** A支持智能体每周评论50个随机对话。

每次更改提示词、模型、分块策略或检索管道时，我们都会运行这些评估。如果没有评估，我们就无法判断更改是改进还是回归。

现在，是时候讨论部署和服务了。

## 第 7 步：部署和服务 {#step-7-deployment-and-serving}

现在我们交付系统。

- **推理：** 使用模型 API。没有这种规模的自托管 GPU。自动扩缩容由提供商处理。
- **API 网关：** 聊天的单个端点。每个用户的速率限制（每天 50 条消息，每分钟 10000 token）。
- **Streaming：** SSE 在负载均衡器上具有较长的超时（我们配置了 5 分钟超时，而不是默认的 30 秒）。
- **降级回退:** 如果主模型宕机，自动切换到辅助模型。
- **防护机制:** 输入防护机制阻止 PII 和提示注入。输出防护机制检查偏离主题的答案和 PII 泄漏。
- **隐私：** 切勿在生产日志中记录完整的提示词和响应（我们首先编辑 PII）。
- **Rollout：** 首先作为金丝雀部署到 10% 的用户。观察指标。只有在质量保持不变的情况下才能实现 100% 推广。

最后一步是监控。

## 第8步：监控 {#step-8-monitoring}

一旦系统上线，我们就不能走开。我们持续监控它。

我们追踪：

- **L延迟：** TTFT，总响应时间，每秒 token 数。
- **Cost：** 每个用户 token、每天成本、每个功能成本。
- **Quality：** 用户的赞成和反对反馈。升级率。忠诚度得分来自抽样对话。
- **Errors：** API 超时、空响应、中断的流、重试。
- **缓存命中率：** 、提示词缓存命中率、语义缓存命中率。
- **Drift：** 用户问题是否随时间变化？帮助中心的文章是否偏离现实？
- **工具/检索运行状况：** 混合搜索是否返回相关的文本块？ 重排序模型是否有所改进？

我们设置警报：

- 每日费用超过 200 美元。
- 平均延迟超过 3 秒。
- 用户满意度（点赞率）跌破80%。
- 忠诚度分数降至 90% 以下。
- 升级率上升到阈值以上（这意味着机器人突然拒绝更多答案）。

如果触发任何警报，我们会调查问题、修复它，并在部署修复之前重新运行评估。

这就是我们在生产中监控AI 系统的方式。

**注意：** 不要过度设计。从最简单的可行设计（单个 LLM 调用）开始，仅在需要时增加复杂性。我们以后随时可以添加向量数据库。我们以后随时可以添加智能体。过早的复杂性是最常见的错误。

如果我们遵循这 8 个步骤，我们就可以从头开始设计任何AI 系统，无论是在面试中还是在实际生产中。
